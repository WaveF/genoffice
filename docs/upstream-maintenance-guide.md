# NexOffice 上游变更适配维护指南

> 本文定义如何持续参考 `genspark-ai/genoffice` 上游更新来维护 NexOffice。上游是问题、设计思路和回归测试的来源；NexOffice 不直接将上游 `main` 合入实际工作分支，也不默认照搬上游实现。

## 目标与边界

NexOffice 是以本地编辑器与外部 MCP 为核心的分支。维护上游更新时应尽量吸收编辑器可靠性、文件兼容性、性能、交互和测试方面的改进，同时保持以下边界：

- 不重新引入内置 AI 对话、AI Provider、Genspark 账户、积分、云项目、分析或上游更新渠道。
- 不把本机文件路径、用户数据或权限扩展暴露给 MCP。
- 不直接 merge 上游 `main`，不以批量 cherry-pick 代替适配设计。
- 不因“上游已有实现”跳过 NexOffice 的类型检查、测试和手工验证。

## 分支约定

- `main`：上游基线参照分支。除经过明确评估的同步操作外，不在其中开发 NexOffice 功能。
- `mcp-only`：NexOffice 的实际集成工作分支。
- `upstream-*`：针对一个已确认适配单元创建的短期分支，例如 `upstream-markdown-save-close`。完成验证后合入 `mcp-only`，并删除短期分支。

上游检查可通过临时 fetch 完成，不要求把官方仓库永久添加为 remote：

```bash
git fetch --no-tags https://github.com/genspark-ai/genoffice.git main
git log --reverse --format='%h%x09%ad%x09%s' --date=short main..FETCH_HEAD
```

该命令只更新 `FETCH_HEAD`，不会移动本地分支或工作区。

## 每轮审计流程

### 1. 固定审计范围

记录：

- NexOffice 基线 SHA（通常是 `main`）。
- 上游目标 SHA。
- 比较得到的提交数、日期范围和提交列表。

若上游存在 `Sync snapshot` 等聚合提交，必须继续按文件、PR 或具体子功能拆分；不得把整包提交直接认定为可采纳或不可采纳。

### 2. 形成变更适配台账

每个独立功能或修复都应填写一项，而不是只按 Git 提交逐项机械记录。

| 字段 | 要求 |
| --- | --- |
| 台账 ID | 如 `UP-2026-08-31-01`，在本轮内唯一。 |
| 上游来源 | 提交 SHA、PR、文件或链接。 |
| 文字化问题 | 描述修复什么用户可感知的问题，不复制代码。 |
| 上游方式 | 简述其实现策略、关键约束和测试方式。 |
| 耦合审计 | 见下方“分类规则”。 |
| NexOffice 决定 | 采纳、适配采纳、暂缓、明确不采纳之一。 |
| 本地落点 | NexOffice 对应模块、预期 API/行为变化。 |
| 验收 | 自动化测试、手工验证和回归风险。 |
| 状态 | 待审计、待实施、实施中、已验证、已关闭。 |

台账建议按日期放在 `docs/upstream-sync/`；本指南不承担每轮的具体记录，避免它不断膨胀。

### 3. 做依赖与边界审计

不能只根据提交标题判断“与 AI 无关”。必须检查所涉文件、调用路径、设置项、IPC 和依赖包，并标记为：

| 分类 | 含义 | 默认处理 |
| --- | --- | --- |
| 独立可采纳 | 与内置 AI、账户、云或分析无调用依赖。 | 优先适配。 |
| 可拆分 | 功能本身有价值，但提交混入 AI/账户等无关改动。 | 提取无关部分后适配。 |
| 强耦合 | 依赖 AgentLoop、AI Provider、Genspark 登录、积分、云项目或分析。 | 默认不采纳。 |
| 架构冲突 | 与 MCP-first、NexOffice 品牌或本地优先策略冲突。 | 明确不采纳，并记录原因。 |

### 4. 决定适配方式

“适配采纳”是常态。实现时应：

- 先根据文字化问题和上游测试理解预期行为。
- 使用 NexOffice 当前的包名、IPC、品牌、MCP 权限模型和本地存储方式重新实现。
- 可以参考上游算法、测试数据与边界条件，但不复制其 AI/账户调用链。
- 对用户可见行为、文件格式或 MCP schema 的变化，补充迁移和兼容性说明。

只有在变更局部、无架构冲突且历史清晰时，才可以考虑局部 cherry-pick；仍须先在 `upstream-*` 分支验证，并在台账中说明理由。

## 实施优先级

按以下顺序处理已确认可适配项目：

1. 数据安全、保存、关闭、恢复和文件损坏风险。
2. 与 AI 无关且低耦合的编辑交互正确性。
3. 性能、流式读取、字体、渲染和大文件稳定性。
4. Docs / Sheets / Slides 的文件兼容性与高价值编辑能力。
5. 仅在能彻底剥离 AI/账户依赖后，再考虑原本来自 AI 功能的通用底层改进。

## 实施与验收流程

对每个台账项：

1. 从 `mcp-only` 创建一个范围清晰的 `upstream-*` 分支。
2. 先添加或移植能够复现问题的测试；必要时补充最小手工复现文件。
3. 以 NexOffice 架构实现修复，避免引入已下线的依赖。
4. 运行对应 workspace 的 typecheck、定向测试，以及风险相称的全量测试或 e2e。
5. 在台账中记录实际提交、验证命令、结果和未覆盖风险。
6. 合入 `mcp-only` 并删除短期分支；不要把未验证的上游同步长期堆积。

## 单轮收束条件

一轮上游审计在满足以下条件后结束：

- 该轮范围内的每项变更都有台账结论。
- 可采纳项已进入独立实施计划，或已明确暂缓原因和触发条件。
- 已实施项拥有对应验证证据。
- `mcp-only` 没有引入内置 AI、账户、积分、云项目、分析或上游更新渠道的回归。
- 文档记录了本轮审计的上游 SHA，下一轮从该 SHA 之后继续。
